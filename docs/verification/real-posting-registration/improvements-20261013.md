## 누가 모집 상태를 바꾸는가

**DB의 상태를 변경하는 스케줄러는 없다.** 기존 서버가 조회 요청마다 `AnnouncementQueryRepository`의 Asia/Seoul `Clock`으로 모집 상태 필터를 계산하고 있었다. 이번에는 화면도 같은 경계를 사용하도록 맞췄다.

```text
저장된 시작·마감 시각 + 수동 마감 여부
    ├─ 서버: 조회 요청 + 한국 시각 Clock → 검색 결과 포함 여부
    └─ 화면: 현재 시각을 1초마다 확인 → 상태 문구·지원 버튼
                  목록은 30초/탭 복귀마다 API 재조회 → 카드 진입·이탈
```

- 수동 마감이면 기간과 관계없이 CLOSED.
- 시작 전 UPCOMING, 시작 시각 이상·마감 시각 이하 OPEN, 마감 시각을 지난 뒤 CLOSED.
- 미확인 일정은 화면에서 ‘일정 미확인’. 공개 완성도 검증이 불완전한 신규 공고의 공개를 차단한다.
- OPEN만 ‘지원하기’, 그 밖에는 ‘원문 확인’. 화면 갱신을 위해 상세 API를 반복 호출하여 조회수를 올리지 않는다.
- 목록 재조회 실패 시 기존 카드·검색 조건을 보존하고 다시 확인 버튼을 제공한다. 요청 세대 번호로 오래된 응답이 새 검색을 덮지 못하게 한다.

실제 cmux에서 별도의 합성 공고 ID 14를 공개했다. 짧은 미래 모집 기간을 입력하고 **시계를 조작하거나 새로고침하지 않고 기다렸다**. 아래는 경계 그 자체의 정밀 시각이 아닌 실제 관찰 시각이다. 정확한 포함 경계는 서버 Clock 테스트와 화면 테스트가 따로 검증한다.

| 한국 시각 | 열린 상세 화면 | 버튼 | 서버 검색 결과 |
| --- | --- | --- | --- |
| 15:33:22.680 | 모집 예정 | 원문 확인 | UPCOMING에만 14 포함 |
| 15:33:40.835 | 모집 중 | 지원하기 | OPEN에만 14 포함 |

열어 둔 OPEN 목록도 30초 주기 재조회로 카드가 들어왔다가 나갔다. 검색 조건에 표시되는 제목을 카드로 세지 않고 `.job-grid` 실제 카드만 확인했다. **자동 전환 구간 전후의 저장된 날짜와 `recruitmentClosed=false`는 변하지 않았다.** 이후 명시적인 UI 편집으로 기간을 현재 시각 전후로 넓히고 수동 마감을 켜면 CLOSED, 해제하면 OPEN으로 돌아오는 것도 확인했다. 현재 합성 공고의 날짜가 달라진 것은 이 후속 수동 편집 때문이다.

## 책임·이름·공개 계약 검토

`RecruitPeriod`는 알려진 날짜 순서를 지키며 미확인 경계는 허용한다. `Announcement.changePublication`은 공개·검토에 필요한 완성도를 지킨다. DTO는 HTTP 입력 검증을, `ExController`는 도메인 예외의 HTTP 400 변환을 맡는다. 도메인에서 HTTP 타입을 참조하지 않는다.

`AnnouncementSourceKey`가 URL 및 원문 식별 키를 만들고 Repository가 기존 키 없는 행까지 중복을 조회한다. Service가 저장 흐름을 조정하며 DB UNIQUE가 새 동시 요청을 최종 보호한다. `RecruitmentRole`은 개별 직무의 조건, `Description.salaryPeriod`는 급여 단위, `referenceUrls`는 보조 출처를 소유한다. 제목 유사성만으로 자동 병합하지 않는다.

프런트 `RecruitmentFactsFields`는 props/event 기반 입력, API 모듈은 multipart 직렬화, `recruitmentState`는 시간 판정, `useRecruitmentTime`은 표시 시각과 타이머 수명주기를 맡는다. 기존 목록의 요청 세대·페이지 상태 소유권은 유지했다. Vue 컴포넌트를 SOLID 점수로 평가하지 않고 표현·상태·API 경계로 검토했다.

기존 JSON `language`, `position`, `recruitmentClosed`와 라우트는 유지하고 새 필드를 추가했다. `language`의 광범위한 기술 태그 의미를 유지한다. `recruitmentClosed`는 수동 종료 입력이며 계산된 현재 모집 상태로 이름을 바꾸지 않았다. 각 변경의 바인딩·응답·저장 후 재조회는 Controller/Service/브라우저 검증에 포함했다.

## 운영 반영 조건과 남은 한계

운영 DB에는 변경하지 않았다. 기존 DB에는 먼저 [원문 식별 키 SQL](../../../src/main/resources/db/manual/announcement-source-identity.sql), [모집 사실 SQL](../../../src/main/resources/db/manual/announcement-recruitment-facts.sql)을 적용해야 한다. 기존 스키마에 SQL 적용 후 validate 기동과 기존 행 보존은 자동 테스트로 확인했다. 기존 금액의 null 단위는 YEAR, 새로운 조건은 null/빈 목록이다. 과거 중복을 자동 병합·삭제하거나 식별 키를 무조건 역채움하지 않는다.

시간 전환은 **등록된 일정**을 기준으로 한다. 외부 기업이 일정을 바꾸거나 조기 마감한 사실을 자동 수집하지는 않는다. 이 경우 운영자의 일정 수정·수동 마감이 필요하다. 화면은 사용자 기기 시계와 브라우저 타이머를 쓰므로 시계 오차·백그라운드 타이머 지연이 가능하며, 목록 반영에는 정상 상황에서도 최대 약 30초가 걸린다.

일자만 있는 모집 정보의 독립적인 date-only 모델·공개 정책, 원문 미기재와 조사 중의 별도 상태 enum, 대용량 포스터의 자동 압축·분할은 이번 구현에 포함하지 않았다. 슈어소프트 원본 8.4MiB 포스터의 5MiB 첨부 제한은 그대로이며 텍스트 초안으로 검증했다. 구조화된 역할은 확인한 범위를 담을 수 있게 한 것이며 전체 기업의 모든 세부 직무를 복원하거나 자동 분류한 것은 아니다.
