## API 계약

라우트·인증·기존 단건 필드를 유지한다. 요청의 `username`은 기존처럼 작성자·권한을 결정하지 않으며 인증 주체의 ID를 사용한다.

| 요청 | 성공 응답 | 오류 |
| --- | --- | --- |
| `GET /api/answer/{questionId}` | 200, `{content, nextCursor, hasNext}`, 최신 ID부터 최대 20건 | 미인증 401, 없는 질문 404 |
| `GET /api/answer/{questionId}?before=<cursor>` | 200, 같은 질문의 `answer_id < before`, 최대 20건 | Long 범위의 정수 문자열이 아닌 커서 400 |
| `POST /api/answer/save` | 기존 200 유지, 생성한 QuestionAnswer 객체 1건 | 기존 인증·없는 대상·입력·서버 오류 계약 유지 |
| 일반·관리자 답변 수정/삭제 | 기존 라우트·응답·소유권 유지 | 이번 단계에서 새 본문·빈도 제한을 추가하지 않음 |

페이지의 `content` 항목은 `answerId, username, content, recommend, dislike, myReaction`을 유지한다. `hasNext`가 참일 때 `nextCursor`는 마지막 반환 ID의 10진 문자열이며, 마지막 페이지는 null이다. 빈 결과는 다음과 같다.

```json
{"content": [], "nextCursor": null, "hasNext": false}
```

- 페이지 크기는 서버 고정 20이다. 요청 파라미터로 상한을 늘리지 못한다.
- 로컬 fixture의 음수 ID를 포함하여 Long 범위의 커서를 허용한다. 커서가 가리키던 행이 삭제돼도 숫자 경계로 조회한다. 다른 질문의 ID를 전달해도 question 조건을 유지한다.
- 쿼리 자체에 최대 21행 제한과 ID 내림차순을 적용한다. 21번째 행은 다음 존재 확인용이다. 본문·작성자 로딩도 최대 21행으로 제한하며, 전체를 읽은 뒤 메모리에서 자르지 않는다.
- 필요한 답변 필드·작성자 이름의 DTO projection을 사용하여 부모 컬렉션·작성자 roles를 로딩하지 않는다. COUNT 전체 조회를 추가하지 않는다.
- 반환할 최대 20개 ID의 내 반응만 읽는다. 빈 페이지는 반응 조회를 생략한다.
- 단건 저장 응답의 반응은 초기 `NONE`, 집계는 0이다. 저장 응답을 만들기 위해 기존 답변 목록을 조회하지 않는다.
- 기존 배열 반환 경로를 우회 엔드포인트로 남기지 않는다. 프런트 타입·호출부·fixture·REST Docs를 함께 바꾼다.
- 두 저장소를 같은 릴리스로 전달해야 한다. 구버전 프런트는 바뀐 응답을 읽을 수 없으므로 배포 순서 또는 트래픽 전환을 전달 단계에서 다룬다.

## 상태 소유자와 객체의 협력

```text
QuestionAnswer(Vue 렌더링·이벤트)
        │
        ▼
답변 composable(목록·커서·입력·요청 세대)
        │
        ▼
answers API(페이지·단건 타입) → AnswerController(HTTP·인증 ID)
                                    │
                                    ▼
                               AnswerService
                               ├─ 새 답변 생성·트랜잭션·단건 조립
                               ├─ 제한된 페이지·내 반응 조립
                               └─ Repository → DB

반응 변경 → 기존 useContentReaction → ContentReactionService → 반응·집계 commit
```

- `AnswerService`: `createAnswerAndList`를 반환 효과에 맞게 `createAnswer`로, 전체 목록 `findByQuestion`을 `findAnswerPage`로 바꾼다. 모든 호출부·테스트·문서를 함께 갱신한다. 생성은 기존 트랜잭션 안에서 commit하며, 조회는 read-only다.
- `Answer.createFor`: 새 답변의 FK 소유 측인 member·question을 연결하며 역방향 `getAnswers()`를 초기화하지 않는다. 기존 관계 이동 helper의 계약은 유지하고 새 생성 경로에서 사용하지 않는다. 별도 DB 재조회·기존 질문 삭제 cascade를 검증한다.
- `ContentReactionService`는 계속 반응 쓰기의 유일한 소유자다. 페이지 조회의 반응 읽기가 소유권 검사를 약화하지 않는다.
- 답변 composable은 목록·커서·작성 입력·오류·초기/추가 로딩·저장·요청 세대를 소유한다. Vue는 렌더링·props/event로 협력하고, API 모듈은 HTTP 변환을 맡는다. 단순 위임 클래스나 추측성 인터페이스는 만들지 않는다.
- 저장 SQL과 페이지 SQL이 기존 답변 컬렉션 규모에 비례한 읽기를 하지 않는지 실제로 확인한다. 객체 이름·효과와 JSON 공개 계약을 같이 리뷰한다.

## 사용자 화면과 실패·경쟁 조건

1. 처음 최대 20건을 표시하고 다음 페이지가 있으면 ‘답변 더 보기’를 표시한다. 클릭하면 기존 목록 아래 추가한다. 전체 답변은 끝까지 읽을 수 있다.
2. 개수는 ‘표시된 답변 N개’로 표현한다. 이를 전체 답변 수로 표시하지 않는다.
3. 저장 성공은 새 답변 1건을 맨 앞에 추가하고 그때 입력을 비운다. 기존 커서는 유지하며, 저장 후 전체 목록을 재조회하지 않는다.
4. 더 보기 중에도 작성·저장을 가능하게 한다. 저장 단건과 페이지 응답은 현재 목록에 합치고 ID 중복을 제거한다. 응답 순서가 뒤집혀도 새 답변·이미 표시한 반응을 잃지 않는다. 추가 조회 완료가 저장 성공을 덮거나 저장 응답이 이전 답변을 지우지 않는다.
5. 같은 더 보기·같은 저장의 중복 클릭은 각각 막는다. 초기 로딩에서 새 질문의 목록이 준비되기 전까지 기존 로딩 표시를 유지한다.
6. 추가 조회 실패는 기존 목록·커서·작성 입력을 보존하며 같은 경계로 재시도한다. 저장 실패도 입력과 기존 목록을 유지한다. 기존 인증 오류 처리와 다른 서버 오류를 구분한다.
7. 질문 이동·unmount 뒤 도착한 조회·저장 응답은 폐기한다. 이전 질문의 결과로 새 질문의 목록·입력·오류를 바꾸지 않는다.
8. 추천·비추천·전환·취소·새로고침의 기존 동작을 유지한다. 다른 페이지를 추가할 때 이미 읽은 답변의 확정된 반응 상태를 오래된 데이터로 덮지 않는다.
9. 더 보기 버튼과 오류·재시도는 키보드와 접근성 이름으로 조작 가능해야 한다. 이번 단계에서 임의의 작성 대기시간·길이 차단 안내를 표시하지 않는다.

## 본문: 사용자 길이와 서버 처리 크기의 별도 검토

두 기준은 같은 숫자로 묶지 않는다.

| 기준 | 무엇을 측정하는가 | 결정 방법 |
| --- | --- | --- |
| 사용자 글자 수 | 편집기에 작성한 Markdown 원문. HTML 변환 뒤 태그·escaping 증가분을 사용자의 작성량으로 세지 않음 | 기존 편집기의 코드 포인트 기준과 긴 코드·한글·이모지 사례를 검토한 뒤 제품 상한 결정 |
| 서버 요청 크기 | 실제 JSON 요청의 UTF-8 바이트, 서식 HTML·필드·JSON escaping 포함 | 정상 입력의 변환 비율과 파싱·정제·저장 비용을 측정하여 별도 처리 예산 결정 |
| 정제·저장 결과 크기 | sanitizer 이후 HTML의 UTF-8 바이트·DB 저장량 | escaping과 정제 후 확장 사례를 측정하여 요청 크기와 함께 결정 |

검토에서는 긴 코드 블록·표·링크·한글·이모지·HTML entity를 포함한 작성 사례를 준비한다. 원문 글자 수 → 렌더링 HTML → 직렬화 요청 바이트 → 정제 결과 바이트를 기록한다. 편집기의 코드 포인트 수가 가족 이모지처럼 보이는 글자 수와 다른 사례도 명시하고 제품의 세기 기준을 정한다.

서버 요청 상한을 도입할 때는 Content-Length만 신뢰하지 않고 실제 읽은 바이트를 제한해야 한다. 헤더 누락·분할 전송·지원 압축이 있다면 해당 경계까지 검증한다. JSON 변환·sanitizer가 큰 입력을 처리한 뒤 거절하는 검사만으로 수신 자원 보호를 완료했다고 판단하지 않는다.

길이 또는 크기 제한을 적용하는 후속 단계에서는 일반 생성·일반 수정·관리자 수정의 우회 여부, 초과 오류 코드·안내, 입력 보존, 레거시 본문 보존을 함께 정의한다. 현재 단계는 이 상한들을 구현하지 않는다.

## 생성 빈도: 정상 사용 사례와 부하로 결정

‘15분 10건’을 확정하지 않는다. 다음 자료를 확보해 작성 흐름을 막는 구간과 서버가 부담되는 구간을 구분한다.

- 정상 사례: 한 질문에 긴 답변 1개, 여러 질문에 짧은 답변을 연속 작성, 작성·수정 반복, 실패 뒤 재시도. 본문 내용 자체를 수집하는 대신 필요 최소한의 빈도·크기 자료를 사용한다.
- 입력 분포: 성공 생성 수와 간격, 회원별 짧은 구간의 burst, 답변 크기. 실제 이용 자료가 없으면 합성 자료라고 표시하고 ‘정상 사용을 증명했다’고 주장하지 않는다.
- 부하 실험: 승인된 로컬 격리 환경에서 회원 수·본문 크기·동시 요청 수·요청률을 통제하고 성공/실패/지연·CPU/메모리·DB 비용을 기록한다. 운영 DB·유료 클라우드를 부하 대상으로 쓰지 않는다.
- 정책 결정: 관찰 결과와 실행 환경의 처리 예산을 근거로 후보값·관찰 기간·조정 방법을 제시한다. 창 방식, 성공과 실패 중 무엇을 세는지, 사용자 대기·입력 보존·서버 간 공유를 그때 확정한다.
- DB 기록과 행 잠금·Redis·입구의 제한 등 구현 수단은 정책을 정한 뒤 가장 작은 적합한 경계를 선택한다. 값이 미정인 상태에서 특정 기록 테이블을 선행 구축하지 않는다.

입력·페이지 크기와 호출 빈도 통제는 [OWASP API4](https://api-security.owasp.org/editions/2023/en/0xa4-unrestricted-resource-consumption/)가 설명하는 자원 보호 경계다. 같은 문서는 빈도를 업무 요구에 맞게 조정하도록 설명한다. 이 일반 지침은 DEMP의 특정 숫자에 대한 근거가 아니다.

## 스키마와 기존 데이터

이번 단계에서 생성 기록 테이블과 제한용 Member 컬럼을 추가하지 않는다. 기존 Member·Answer ID·본문·반응도 backfill하거나 자르지 않는다.

커서 조회용 `(question_id, answer_id)` 인덱스의 기존 유무·MySQL 실행 계획을 확인하고, 필요하면 기존 운영 원칙에 맞는 별도 수동 SQL과 적용·데이터 보존 검증을 제공한다. 실제 운영 DB에 적용하지 않는다. Hibernate `ddl-auto=validate`가 인덱스 존재까지 검증한다고 보고하지 않고, 메타데이터·실행 계획으로 별도 확인한다.

과거의 거대 LOB도 조회할 수 있어 페이지의 레코드 수는 제한되지만 각 본문의 응답 바이트 상한은 보장되지 않는다. 이 잔여 경계는 본문 크기 정책을 정할 때 다룬다.

## 완료 판단과 다음 단계

이번 완료는 단건화·페이지화·화면의 상태 전이·기존 데이터와 반응 보존의 실제 검증으로 판단한다. 대량 생성·대형 본문·전역 요청량까지 모두 해결했다거나 전체 답변 finding을 종료할 수 있다고 보고하지 않는다.

수정 명세와 [TDD 구현 계획](../plans/2026-10-06-bounded-answer-creation-and-read.md)은 승인되었으며 기존 ‘순차적으로 진행’ 선택에 따라 실행한다. 앞선 CI·로그인 변경은 두 PR의 보호된 머지와 main CI까지 완료했다. 이후 본문·빈도 조사 결과를 토대로 정책을 구체화하고, 태그·이미지의 남은 개선으로 이어간다.

## 최종 검토의 ID 정밀도 보완

큰 Long ID 두 개가 JavaScript number에서 같은 값으로 반올림되어 페이지 병합에서 답변이 누락됨을 최종 리뷰에서 확인했다. 이 효과를 Important로 재평가해 같은 수정 단계에서 QuestionAnswer.answerId를 문자열로 직렬화하고 프런트 Answer의 wire 타입을 string으로 고정했다. 필드 이름·서버 내부 Long·반응 endpoint는 유지한다. GET/POST의 안전 정수 초과·Long 양끝·음수 HTTP 타입/값, UI 페이지·저장·정확한 반응 경로 및 MySQL 실제 큰 ID 조회를 검증한다. 프런트·백엔드가 함께 전환하는 계약에 ID의 JSON 타입 변경도 포함되며 본문/빈도 제한을 추가하지 않는다.
